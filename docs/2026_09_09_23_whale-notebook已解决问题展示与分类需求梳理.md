## 1. 背景与需求原文

用户原话（2026-09-09）：

> 小本本需要有个展示的地方，就是我们已经解决了哪些问题？而且问题是不是可以分类？比如系统级别的命令，类似于跑 bash 编码转义这种全局通用的，另外还有某个项目里会用的，比如这个工作区是 Python 的，而另一个工作区是 C#，那么 Python 的避坑经验就不一定适用于 C#。这两个需求对于小本本的数据结构和实现方式可能是一次重构的大挑战。你分析梳理一下这个需求。

## 2. 现状盘点（实机核实）

### 2.1 数据流（v1 → v0.3.0 不变）

```
~/.dsh/sessions/*/<sid>/session.jsonl.zstd（只读）
  → scanner 抽取失败/特征事件 { at, cat, tool, text, ws, sid, file }
  → engine 指纹去重 + 聚簇（canonText/hash36）
  → 候选行 inbox.md（| C### | 类别 | 次数 | 工作区 | 现象(打码) | 时间 |）
    + details/C###.md（v0.3 sidecar：一句话/源引用 sid@时间｜工作区｜日志路径/打码摘录 ≤600 字）
  → 用户逐条确认 → entries/E###-slug.md + INDEX.md + ~/.dsh/AGENTS.md 自动段
```

- **候选行工作区列**只显示 ≤2 个工作区名（cwd 尾段，如 `SandBox1`）；`details/` 源引用含完整 `file`（sessions 内日志路径）。
- **sessions 目录名**形如 `--C-DeepSeekHarnes-SandBox1--`（路径打平包裹）→ 可还原会话所在项目绝对路径，用于定位「项目」与「项目根」。

### 2.2 分类现状：只有一维

- 唯一分类维度 = **category（坑类型）**，16 类：encoding / stale-fs / sandbox-file / sandbox-ep / approval / tool-mode / git-net / secret / session-state / data-access / long-session / timeout / model-api / file-missing / port-busy / other。
- 不存在「适用范围」维度；但**埋点已具备**：事件、候选（详情）、条目（frontmatter `workspaces: []`）三层都带工作区/项目信息。
- 实测现有候选（C001–C012）跨工作区分布很不均匀：C001/C002/C003 出现在多个工作区（天然「全局」），C004/C005 等单工作区（未必项目级——例如 SandBox1 也常做全局性试验）。→ 佐证：**适用范围不能由统计自动判定，需要入库时人工语义判定**。

### 2.3 展示现状：无「已解决」视图

| 展示面 | 内容 | 缺什么 |
|---|---|---|
| 会话内提醒小列表 | 待审候选（mine.cjs --check） | 只覆盖待审 |
| 决策箱悬浮面板 | 待审候选 + 详情 + 删除 + 转讨论（v0.3） | 只覆盖待审 |
| INDEX.md | 全部 active 条目索引（按 category 分组） | 静态文件、非「墙/史」、无处置记录 |
| archive/*.md | 已处理候选行（含处置：入库 E### / 面板删除 / 忘掉） | 无展示入口 |
| --stats | 次数/类别/工作区分布 | 聚合统计，非问题清单 |

**「已解决」的数据事实已经存在**：entries（active = 已确认对策）+ archive（处置史）。缺的只是一个聚合与展示入口。

### 2.4 关键机制核实（本次新发现）

DSH `dsh-agent-instructions` 插件（@deepseek-ai/dsh-agent-instructions，lib/index.js 实读）原生支持**两级指令注入**：

1. 用户全局：`$DSH_HOME/AGENTS.md`（= 现小本本自动段所在）。
2. **项目链**：从「项目根（向上找 .git 等 marker）」到「会话 cwd」路径上每一级目录中的 `AGENTS.md` / `CLAUDE.md`（及其 `.local` overlay）——新会话作为 baseline 注入；会话内 read/write/edit 触碰后热同步。

结论：**「项目级经验只在对应项目会话自动生效」的载体，DSH 已原生提供**（项目根放一个带标记区的 AGENTS.md 即可），小本本不需要自造注入通道。代价是文件出现在用户项目目录（git 树）内，需要按项目逐个知情与部署管理。

## 3. 需求拆解与语义澄清

### 3.1 需求 A：先定「已解决」的口径（决策点 1）

- **口径 ①（轻 · 推荐起步）**：「入库」= 踩过坑 + 已确认对策 = 该问题已被处理/有解。展示源 = `entries(active)` + `archive` 处置记录。零新增采集，数据全在库。
- **口径 ②（重 · 二期可选）**：利用引擎 `state.seenFingerprints`（指纹全历史）做**复发检测**——条目覆盖的坑，在入库之后是否又出现新指纹：
  - 未复发 → 可标「已解决 ✔」；
  - 复发 → 标「复发 ⚠ 需回炉」（提示重审该条目）。
  - 这能真正回答「解决了吗」，但需动 engine/state 模型（时间窗口、指纹↔条目映射），是本需求里最大的数据层工作之一。

**两口径可叠加**：一期按 ① 建墙，二期按 ② 给墙上「复发」状态灯。文档建议：先 ① 后 ②。

### 3.2 需求 B：新增「适用范围」维度（与 category 正交）

- **二维分类**：`类别 category`（坑类型）× `适用范围 scope`（global | project）+（project 时的）`projects: [项目名…]`。
- **允许「一条经验适用多个项目」**：projects 白名单式（例如两个 Python 项目共用一条 Python 经验，而 C# 项目不适用）——避免「全局/单项目」二元的僵硬。
- **判定是语义判断，不是统计判断**：引擎只提供证据（涉及工作区/项目集合），最终 scope 由入库审核时人定（AI 给建议 + 用户确认），与现状「先展示后确认」流程天然兼容。
- **反向推论（去噪音的关键）**：一旦某条标记 `scope: project`，它**不应进入全局自动段 top12**（否则 C# 会话照样收到 Python 规则，正是用户反对的）。project 规则需要有自己独立的生效/查询通道（见 §6）。

## 4. 分类模型草案

```
维度 1 类别 category  ← 现状 16 类，不变
维度 2 适用范围 scope ← 新增
        ├─ global   ：所有工作区会话普遍适用（例：bash/PowerShell 中文编码转义、沙箱纪律）
        └─ project  ：仅列出的项目适用（例：某 Python 工作区「环境变量未配 Python 路径」；
                      同一条可同时适用 PythonA、PythonB，不适用 C# 项目）
维度 3 处置状态       ← 现状已有：active（生效）/ disabled（忘掉/停用）＋ archive 处置史
                        （二期：+ 复发灯）
```

直观理解：**「墙」先按 维度 2 分区（全局区 / 项目区），区内按 维度 1 分组，行上标 维度 3 状态**。

### 5.3 展示/墙的数据源

`entries(active/disabled)` + `archive` 处置记录；全部已打码、只读，无新增隐私面。

## 10. 决策与答疑记录（2026-09-09 用户反馈）

### 10.1 决策 ①：轻口径 定案

「已解决」= 入库（踩过坑 + 已确认对策）即视为已处理。展示源 = entries(active/disabled) + archive 处置记录。复发检测（口径②）不在一期范围，留作未来可选增强。

### 10.2 答疑 ②：文档墙 vs 面板（用户疑问：是否仅展示不同、后台数据与存储一致？）

**答：数据层完全一致——同一份数据（entries/ frontmatter + archive 处置记录），经同一 viewmodel 纯函数出可渲染结构，不存在两套存储、不会两边不同步。差异全部在呈现与消费层：**

| 维度 | 文档墙（A1） | 面板 tab（A2） |
|---|---|---|
| 形态 | 一个 Markdown 文件（INDEX.md 升级版），入库/忘掉动作时重写落盘 | GUI 悬浮面板内动态渲染列表：host 只读 API + 浏览器 bundle |
| 谁能看 | 人（编辑器）+ **任何 DSH 会话的 agent**（read 文件即可回答「解决过哪些问题」） | 只有**人**在 dsh web GUI 可见；agent/模型看不到面板 |
| 交互 | 无按钮、纯阅读；操作仍靠会话里说 | 可筛选/展开/按钮（写操作仍「先展示→确认」，红线不变） |
| 部署生效 | 零部署：repo 写文件即生效 | 升级走 deploy-web + 重启 dsh web 才生效 |
| 成本 | 低（生成器 + 落盘时机） | 中（host 端点 + client 渲染 + 测试 + 重启验收） |
| 定位 | 「内容优先」的信息面 | 「交互优先」的操控面 |

### 10.3 答疑 ③：B2 成本句逐词解释

原句：「跨项目部署/更新/卸载需扩展 I/D 足迹与工具；每项目文件出现在用户 repo git 树，须逐项目知情」。

- **I/D 足迹**：小本本 lifecycle 把所管理的外部文件按段登记（I 集成 = AGENTS.md 标记区、skill；D 数据 = `~/.dsh/whale-notebook/`），清单在 `.lifecycle/manifest.json`，卸载按清单清理。现状 I 集成点只有 1 个（全局 `~/.dsh/AGENTS.md` 标记区），路径固定、清单静态。B2 后要为**每个适用项目根**各维护一个标记区文件 → I 足迹从 1 个固定位置变成 N 个**随工作区出现而动态增长**的位置，清单登记与卸载清理逻辑都要扩展。
- **工具**：部署/同步管理脚本。现在入库只重写 1 个 AGENTS.md；B2 后一条 `scope: project, projects:[A,B]` 的规则增删改要同步重写 A、B 项目文件内的标记区（每步仍先展示确认）；「忘掉/停用」要同步摘除各项目文件行；卸载 remove 要询问项目内标记区文件去留。
- **git 树 / 逐项目知情**：项目根通常是 git 库根，写入后 AGENTS.md 出现在该项目 git 工作树（用户 `git add .` 可能带入项目仓库历史——内容虽只含通用对策行，仍不应进入用户 repo），故对每个**新**目标项目下笔前须单独征求同意并约定 git 策略。
- **实测修正（2026-09-09）**：`C:\DeepSeekHarnes\SandBox1` 根**无 .git** → 若试点选 SandBox1，文件不进任何 git 库，git 干扰为零；`C:\ClaudeCode\SillyTavern-Agent`、`source-repos\…\LearningWebMediaCenter` 推断路径**目录已不存在** → sessions 目录名打平反推绝对路径**不可靠**；B2 的目标项目清单必须以会话记录的真实 cwd（session 头字段）为准，取不到的旧会话跳过。

### 10.4 答疑 ③：空项目的影响（用户疑问）

分四种「空」，结论均无碍：

1. **项目存在但无任何规则适用** → 懒创建：不写文件、零影响；第一条命中规则才创建标记区文件。
2. **项目目录已不存在/够不到**（实测 SillyTavern-Agent 即此例）→ 部署跳过，不报错、不影响其他项目。
3. **新项目将来出现** → 无历史规则则不被写入任何东西。
4. **曾写入、后规则全清空** → 边界点：若留「空壳 AGENTS.md（只有标记区）」，DSH 注入机制**仍会把空文件渲染成『Instructions from: …』空节**（已读 dsh-agent-instructions 源码核实：空文件亦被注入）——每会话多一段无意义头。故清空时应**删除文件恢复原状**（文件若是小本本纯创建则删除即恢复，但会先列入足迹清单供用户确认）。

**一句话：B2 是「有规则才写、无规则不碰、全清则删」的惰性机制，空项目无影响。**
