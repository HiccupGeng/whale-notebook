# 小本本「已过期」机制（方案 C）开发实施计划

> 日期：2026-10-20 ｜ 版本：v0.8.0 提案 ｜ 作者：待填 ｜ 目标插件版本：0.7.12 → 0.8.0（数据向前兼容，无需迁移）

## 1. 背景与目标

「已解决墙」的经验条目进入 `~/.dsh/AGENTS.md` 自动段后，会被 DSH 的 agent-instructions 机制注入**每一个会话**。当前注入成本（估算）：

| 组成 | 字符 | tokens（中文 ≈1.5 字/token） |
|---|---|---|
| 6 条规则行 | ≈930 | 600–700 |
| 尾注 3 行（自动采集提醒最长） | ≈700 | 450–520 |
| 标题/状态行/空行 | ≈180 | ≈120 |
| 隐私区 | ≈150 | ≈100 |
| **合计** | **≈2,000** | **≈1.3k / 会话** |

问题不在绝对量，而在**只增不减**：注入集合 = `active ∩ scope≠project`，按 `occurrences` 降序取前 12（`inject/agents.cjs:39-40`），而 `occurrences` 只会累加。结果是老规则永久占坑，即使它对当前环境已不成立。

**目标**：

1. 让不再有效的规则**退出注入段**，但条目本身**一字不动地保留**，可原样恢复；
2. 机制本身 **token 增量为 0**，净效果为负（省）；
3. 过期痕迹在「已解决墙」可见、可查、可续期。

**非目标**（明确排除）：

- 不把条目文件或规则文本搬到 `expired/` 等新目录（事实源会分裂，恢复易漂移）；
- 不在 AGENTS 自动段里保留「已过期清单」（那是注入噪音，反向 +150~200 tokens/条）；
- 不做会话内自动重建（写用户全局记忆 + 制造 lifecycle「待登记」，与既有纪律冲突）。

## 2. 设计

### 2.1 状态模型（三态）

```yaml
status: active | expired | disabled
expiredAt: 2026-10-20      # 可选；仅 status=expired 时有意义，展示与审计用
```

- `active`：有效，参与注入与墙的全局区/项目区；
- `expired`：曾有效、现在不再适用（环境变了/已复核为无效），**不进注入**，墙中单列；
- `disabled`：用户主动「忘掉」，**不进注入**，墙中单列（既有语义，保持不变）。

状态缺省值仍为 `active`（`store/repo.cjs:472`），旧条目零迁移。

### 2.2 事实源不变

条目文件是唯一事实源，过期只改 frontmatter 的三个字段，**正文、`rule`、`occurrences`、`sources` 一律不动**。这是「原样恢复」的物理保证。

### 2.3 生效路径（必须显式）

```
标记过期（改 frontmatter）
  → mine.cjs --render-rules（预览新段）
  → 用 edit 替换 AGENTS.md 标记区
  → lifecycle/cli.cjs check --adopt（重新登记基线）
```

自动段是生成物（`inject/agents.cjs:35-58` 纯函数），不跑这一步，下个会话仍注入旧文本——这是本方案最容易踩的坑。

### 2.4 墙分区（过期区用「轻行」）

`INDEX.md` 由 `repo.buildIndexMd` 生成，当前是「全局区 / 项目区 / 🛑 停用」（`store/repo.cjs:505-567`）。改为：

```
## 🐳 全局区（注入）
## 📁 项目区（不注入）
## 🕐 已过期（expired · 不再注入，可续期）   ← 轻行：编号|标题|类别|次数|过期日
## 🛑 停用（disabled · 用户主动忘掉）         ← 轻行同现状
```

轻行不含 `rule` 全文：每条 ≈40–60 字符（30–40 tokens），比全文行（150–200 tokens）省约 4 倍；需要全文时点开面板或 `GET /whale/entry`。

顶部统计行同步为：`active N（全局 x + 项目级 y）｜已过期 z ｜停用 w`。

### 2.5 恢复流程与「原样」边界

恢复 = `status: active`（清 `expiredAt`，更新 `updated`）+ 重建 + `check --adopt`。

- **原样**：`agents.ruleLine()`（`core/schema.cjs:104`）输出 `- 【category】rule`，确定性；只要 `rule` 文本没动，恢复后注入段里的那一行**字节一致**。
- **不原样（必须告知用户）**：
  1. **位置**：段内顺序按 `occurrences` 降序，恢复后可能不在原位置；
  2. **可能回不去前 12**：过期期间别的条目次数在涨，恢复后可能排第 13 名——`status` 回来了，注入没回来。现在只有 7 条不显，条目变多后是必然坑。
  3. 状态行计数、墙中区块位置会变。

对策：恢复动作结束后输出「当前排名 N/前 12」，未进前 12 时明确提示；可选 `pinned: true`（生成时优先占位），留到 P2 再做。

### 2.6 复发联动

- 过期条目**仍参与** `relatedPayload` 的「可能已被覆盖」提示（`ui/server.cjs:121-129`），返回中带 `status`，面板显示「E00x 已过期」——否则同一个坑会在过期后再开一条新候选，墙越滚越大。
- 过期**不会**让候选自动复活：`已处置` 的事实源是归档签名，与 status 无关；同一现象再次出现时按既有「复发」逻辑开候选，此时提示「E00x 已过期且同现象复发，是否续期」。

### 2.7 观测（唯一新增的每会话输出）

`mine.cjs --check` 的摘要行（`collector/engine.cjs:932-953`）追加一段，仅在 `expired > 0` 时输出：

```
已过期 2 条（注入段待重建）
```

约 +20–30 tokens/会话，换掉「过期了但没人知道」的静默失效。

## 4. 数据迁移

- 现有 7 条（E001–E007）：缺省 `active`，**零迁移**。
- 过期操作仅改 frontmatter；不需要写 `state.json`，不需要动归档。
- 回滚：代码回退即可；已标 `expired` 的条目会重新被当作 active 注入（因为旧代码只认 `status==='active'`… 注意：旧代码同样过滤非 active，故回滚后过期条目**仍不注入**，语义安全，不会突然炸出旧规则）。

## 5. token 预算

| 项 | 改动前 | 改动后 |
|---|---|---|
| 注入段（每会话） | ≈1.3k | 每过期 1 条 **−80~145** |
| `--check` 输出 | 1–3 行 | +20~30（仅有过期时） |
| 墙（按需读） | ≈1.4k | 过期轻行 +30~40/条 |
| 面板 | 0 | 0 |

净效果：只要过期 ≥1 条，就是省；收益量级百级，真正的价值是**腾出 top-12 槽位**与减少跨场景误导。

## 6. 验收标准

1. 墙：`INDEX.md` 出现「🕐 已过期」区，轻行不含 rule 全文；顶部统计四项（active/全局/项目/过期）自洽。
2. 注入：把 E002 标为 `expired` 并重建后，AGENTS 自动段不再含该行，状态行显示「已过期 1」。
3. 恢复：标回 `active` 并重建后，该行**文本与过期前逐字节一致**（对比 `ruleLine()` 输出）。
4. 覆盖提示：`GET /whale/related?id=C###` 仍能返回已过期条目，且带 `status: expired`。
5. `--check`：存在过期条目时输出「已过期 N 条（注入段待重建）」，无过期时**不输出**（不增加常态成本）。
6. 旧数据：未改动的 7 条条目行为完全不变（全部自测通过）。

## 9. 后续（独立于本方案，建议同批做）

1. **价值口径替代日历过期**：在修复/复发信号上统计「条目建立后同现象复发次数」，为每条规则给一个有效性数字（`--stats` 输出）。这比手工判断过期更可解释，也是让「小本本到底有没有用」变得可见的唯一办法。
2. **注入瘦身**：尾注提醒句 ≈560 字（≈400 tokens）是单块最贵项，可压到 1 行（≈110 字）；6 条规则中通用好习惯类（读后再改、UTF-8 编码）可降级到项目级或技能内。合计约可省 700 tokens/会话。
